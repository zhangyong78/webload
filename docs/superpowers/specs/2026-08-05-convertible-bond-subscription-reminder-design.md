# A 股可转债申购提醒设计

## 目标

在现有 Windows 提醒程序中增加 A 股可转债申购提醒。每个申购日于 10:00 和 14:00 提醒当天可申购的全部可转债，并复用现有托盘通知、弹窗和邮件渠道。

## 范围

- 自动获取当天可申购的 A 股可转债。
- 提醒内容包含转债名称、转债代码、申购代码和申购日期。
- 每个申购日设置 10:00、14:00 两个提醒档位。
- 程序错过档位后启动时立即补发；若两个档位都已错过，只发送一条合并补发提醒。
- 不增加上市日、中签结果、缴款日或交易操作功能。
- 不改变现有 OKX 提醒规则。

## 数据源

新增独立的可转债客户端，直接请求东方财富数据中心的 `RPT_BOND_CB_LIST` JSON 接口，并按本地日期筛选 `PUBLIC_START_DATE`。

客户端只向程序暴露统一的可转债申购记录，不让接口字段渗透到提醒规则中。首期映射字段如下：

- `SECURITY_NAME_ABBR`：转债名称。
- `SECURITY_CODE`：转债代码。
- `CORRECODE`：申购代码。
- `PUBLIC_START_DATE`：申购日期。

接口请求设置超时并检查响应状态、业务成功标志及数据结构。接口字段缺失或日期无效的记录被忽略；请求或整体解析失败则作为本次检查错误处理。

## 组件与数据流

1. 调度器在程序启动以及每天 10:00、14:00 触发可转债检查。
2. 可转债客户端获取并解析当天申购记录。
3. 提醒规则根据当前时间和当天已发送状态判断正常提醒或补发提醒。
4. 当天所有可申购转债合并成一个提醒事件。
5. 现有通知分发链路把同一事件发送到当前启用的托盘通知、弹窗和邮件渠道。
6. 成功生成提醒后立即保存去重状态，程序重启后继续生效。

可转债数据获取和规则判断与现有 OKX 监控保持独立；它们仅共享调度入口、持久化机制和通知分发能力，避免修改现有活动模型及规则。

## 调度与补发规则

按北京时间的本地自然日计算，状态键使用“申购日期 + 档位”：

- 10:00 前启动：等待 10:00 提醒。
- 10:00 至 14:00 前启动：若 10:00 尚未提醒，立即补发 10:00 档；14:00 正常提醒。
- 14:00 及以后启动：若当天两个档位均未完成，只发送一条合并补发提醒，并把 10:00、14:00 两个档位同时标记为完成。
- 14:00 及以后若仅有一个档位未完成，只补发该档位一次。
- 当天没有可申购转债时不发送提醒，也不把接口失败误判为无申购。

程序持续运行时，10:00 和 14:00 的调度允许少量延迟，并按上述补发规则执行。状态按日期隔离，不影响下一申购日。

## 提醒内容

标题标明“A 股可转债申购提醒”。正文先说明正常档位或补发状态，再逐条列出当天转债：

`转债名称｜转债代码｜申购代码｜申购日期`

若当天存在多只转债，全部放在同一条提醒和同一封邮件中，避免连续弹窗。

## 错误处理

- 网络超时、非成功响应、JSON 结构异常：记录错误，不发送提醒，不更新已发送状态。
- 单条记录字段不完整：忽略该记录并记录诊断信息，其余有效记录仍可提醒。
- 通知渠道发送失败：沿用现有渠道错误处理；其他渠道不受影响。
- 后续检查成功时按补发规则继续处理，无需用户手工清理状态。

## 持久化

在应用状态中增加可转债提醒档位记录，按申购日期保存 10:00、14:00 的完成状态。保持现有 JSON 配置和状态文件向后兼容：旧状态文件缺少新字段时使用空状态。

不保存完整历史行情或公告，仅保存去重所需的最小状态。

## 验证

- 客户端能够解析正常响应中的名称、转债代码、申购代码和申购日期。
- 客户端正确处理空数据、字段缺失、无效日期、超时和异常响应。
- 10:00、14:00 各触发一次，重复检查不重复提醒。
- 10:00 后启动会补发一次，并保留 14:00 正常提醒。
- 14:00 后首次启动只产生一条合并补发提醒，两个档位同时完成。
- 当天多只转债合并到一条提醒。
- 当天无可申购转债时不提醒。
- 旧配置和状态文件仍能加载。
- 现有 OKX 规则、通知渠道和完整测试套件继续通过。
